**`eth0` MAC 单独强调**：`br-lan` 桥的成员口是 `eth0`，它才是接入同一个 LAN 的那个口，撞车比 `eth1` 更致命。`probe-new-device.sh` 对两个口做交叉比对（新机 eth0/eth1 分别与源机 eth0/eth1 四向比），不要只盯 `eth1`。

新机独有的三条状态：

- `dhcp.lan.ignore=1`。新机不发 DHCP，地址由源机发放。改成发放会让客户端随机拿到两套网关。
- `wireless.r3mini_phone_sta.disabled=1` 且 `r3mini_hotspot.main.enabled=0`。新机不跑手机热点 STA，因为热点会把 5 GHz AP 钉到热点所在信道，两台连同一部手机时必然同频争用。
- 5 GHz 用信道 149（中心 155），源机用 48（中心 42）。中国频段下 HE80 只有这两个非 DFS 的 80 MHz 块，不要把两台放进同一块。

新机上**没有**智能出口候选（`r3mini-egress-manager`、`95-r3mini-egress`）。源机上同样没有——该候选至今未部署。

新机 root 已设密码；凭据与 SSH 主机密钥指纹记在本机私密文档 `docs/私密/商家交付信息.md`，不得提交、打印或转发。

## OpenClash “无订阅信息”的根因（2026-07-19 观测，未复测）

> **整节都是 2026-07-19 18:46 的观测，2026-09-03 那轮复核没有重测这一节。** `HTTP 429` 是限流状态，两个多月后大概率已经变了。不要把下面的结论当今天的现状汇报，也不要据此直接去查订阅服务商侧的限流或账号状态——先重跑一次探测拿到当下的响应头再判断。

UI 点击刷新后，配置文件更新时间可以更新，但订阅信息仍显示“无订阅信息”。截至 2026-07-19 18:46，WAN 已接通，出口路径已闭环；当时的根因是远端订阅接口返回 `HTTP 429`，没有返回 `subscription-userinfo` 响应头。

WAN 与公网连通证据：

```text

speed=1000

wan address=192.168.0.30/24

PING_IP_OK
nslookup em.mesl.cloud 223.5.5.5 -> 172.67.73.69, 104.26.12.155, 104.26.13.155
```

订阅接口脱敏探测证据：

```text
SUB_HOST=em.mesl.cloud
SUB_UA=clash-verge/v2.4.5
CURL_RC=0
HTTP_LINE=HTTP/2 429
CONTENT_TYPE=text/plain; charset=UTF-8
CONTENT_LENGTH=17
HAS_SUBINFO=no

fallback UA=Quantumultx
HTTP_LINE=HTTP/2 429
HAS_SUBINFO=no
```

控制器逻辑证据：

- `sub_info_get` 会按当前配置名 `MESL_家宽` 查订阅 URL。
- 当前运行 YAML 没有 `proxy-providers:` 块，因此控制器回退到 UCI 的 `config_subscribe` 地址。
- UCI 中 `config_subscribe[0].name='MESL_家宽'`，与当前配置文件 basename `MESL_家宽` 匹配。
- `fetch_sub_info()` 只有在远端 HTTP 200 且响应头包含 `subscription-userinfo` 时才会构造 provider 数据。
- 当前远端返回 429 且没有 `subscription-userinfo`，所以 JSON 中 `providers=[]`，页面只能显示“无订阅信息”。

不要把这个现象误判为 UI 时间刷新 bug。当前 UI 时间刷新已由 Edge 黑盒验证：

截至 2026-07-19 18:46，仅就“路由器自身的 WAN 链路、WAN DHCP、默认路由、公网 ping 与订阅请求”这一范围，未通过项只剩订阅接口响应头。客户端 DHCP、持续上网、OpenClash 新连接、DNS 泄漏和物理故障转移仍按热点验收文档单独验证。不要高频手动刷新订阅信息，避免继续触发远端 429。等待远端限流窗口恢复后，只点一次刷新并复测 `subscription-userinfo`；如果仍返回 429，改查订阅服务商侧限流、账号状态或订阅接口策略。

### 路径 B：同网段旁路/主路由 LAN 拓扑

继续使用 `192.168.0.242/24` 并只接 `eth0` 时，设备需要明确默认网关和 DNS，否则路由器自身无法更新订阅：

```text
默认网关: 192.168.0.254
上游 DNS: 192.168.0.254 或明确的公共 DNS
```

写入这类配置属于修改 `/etc/config/network` 或相关 DNS 行为。执行前必须：

1. 做当前配置备份。
2. 明确用户选择路径 B。
3. 写入最小变更。

## 可复现只读复核命令

在 Windows 项目根目录执行：

```powershell
python .\openclash-ui-patch\router_readonly.py 192.168.0.242 "date '+%Y-%m-%d %H:%M:%S %z'; ip -4 addr show br-lan; ip route show; /etc/init.d/dnsmasq status; /etc/init.d/openclash status; /etc/init.d/nikki status 2>/dev/null || true; uci -q get network.lan.ipaddr; uci -q get network.@device[0].ports; uci -q get network.wan.device; uci -q get wireless.radio1.channel; uci -q get wireless.radio1.htmode; uci -q get wireless.radio1.disabled; uci -q get r3mini_fan.main.high_up; for f in carrier operstate speed duplex; do [ -r /sys/class/net/eth1/$f ] && printf '%s=' $f && cat /sys/class/net/eth1/$f; done; ping -c 1 -W 2 192.168.0.254 >/dev/null 2>&1 && echo PING_HARD_ROUTER_OK || echo PING_HARD_ROUTER_FAIL; ping -c 1 -W 2 223.5.5.5 >/dev/null 2>&1 && echo PING_IP_OK || echo PING_IP_FAIL"
```

该脚本从 `docs/私密/商家交付信息.md` 提取反引号包裹的候选密码，两台的密码都已记在那里。

**但上面这条命令不能原样套到克隆机上**，两个原因：它只读到 11 条克隆机判据里的 4 条（`lan.ipaddr`、`high_up`、`radio1.channel`、openclash 运行状态），漏掉主机名、`dhcp.lan.ignore`、`ntp`、`radio0.channel`、`r3mini_phone_sta`、`r3mini_hotspot.enabled`、`RM500CNV`、OpenClash 版本、`/etc/rc.d/`；而且它内含 `PING_HARD_ROUTER_OK` 与默认路由检查，克隆机若没接 WAN 会产生假失败。克隆机用下面这条：

```powershell
$env:ROUTER_CMD = 'echo "lan=$(uci -q get network.lan.ipaddr) host=$(uci -q get system.@system[0].hostname)"; echo "dhcp_ignore=$(uci -q get dhcp.lan.ignore) ntp=$(uci -q get system.ntp.enabled)"; echo "high_up=$(uci -q get r3mini_fan.main.high_up)"; echo "ch24=$(uci -q get wireless.radio0.channel) ch5=$(uci -q get wireless.radio1.channel)"; echo "sta_disabled=$(uci -q get wireless.r3mini_phone_sta.disabled) hotspot_enabled=$(uci -q get r3mini_hotspot.main.enabled)"; echo "rm500=$(uci -q get network.RM500CNV 2>/dev/null || echo DELETED)"; echo "openclash=$(opkg list-installed | grep luci-app-openclash)"; echo "openclash_svc=$(/etc/init.d/openclash status)"; echo "fan_autostart=$(ls /etc/rc.d/ | grep r3mini-fan | tr "\n" " ")"'
python .\openclash-ui-patch\router_readonly.py 192.168.0.246
```

源机通过判据：

```text
管理地址与用户指定一致
fan high_up=40000
OpenClash running
Nikki inactive
5G radio1 channel=48, htmode=HE80, disabled=0
如果要更新订阅，则必须存在 default route 且 PING_IP_OK
```

**`channel=157` 这条判据已作废，不要照它去改源机。** 它写于 2026-07-19，当时手机热点 STA 把 radio1 拉到 157 与热点共存。2026-09-03 只读复核到源机 radio1 实际在 **48**。更要紧的是：157 与克隆机使用的 149 落在**同一个 80 MHz 块**（149/153/157/161，中心 155，跨度 5735–5815 MHz），把源机改到 157 会让两台完全同频，正是下方「第二台设备」节明令要避免的。要重新启用手机热点 STA，唯一可行解是**把克隆机从 149 挪到 36–48 那一块**：中国频段非 DFS 只有中心 42 与中心 155 两个 HE80 块，源机一旦被手机热点钉在 155 块，克隆机就只能去 42 块。做法是在**克隆机**上改 `wireless.radio1.channel`（例如 36），改前可用 `SRC_CH5=157 NEW_CH5=36 sh scripts/router/gen-clone-identity.sh` 验算，不报 `CH5_SAME_80MHZ_BLOCK` 即为不冲突。这属于写 `/etc/config/wireless`，须先取得用户明确许可并做改前备份。**不要改源机的 radio1**——它的信道由手机热点决定，改了会断开 STA。

克隆机通过判据（与源机不同，逐条列全）：

```text
network.lan.ipaddr=192.168.0.246
system.@system[0].hostname=immortalwrt-246
dhcp.lan.ignore=1
system.ntp.enabled=1
r3mini_fan.main.high_up=40000
wireless.radio0.channel=6, wireless.radio1.channel=149
wireless.r3mini_phone_sta.disabled=1
r3mini_hotspot.main.enabled=0
network.RM500CNV 不存在
luci-app-openclash=0.47.156 且 openclash running
/etc/rc.d/ 下存在 S99r3mini-fan
```

另有 `scripts/router/probe-new-device.sh`，它是**克隆前的兼容性预检，不是克隆后的整体验收**。严格只读，输出以 `CLONE_PRECHECK_OK`、`CLONE_PRECHECK_OK_WITH_WARNINGS` 或 `CLONE_PRECHECK_BLOCKED` 结尾，被阻断时以 rc=1 退出。克隆机 2026-09-03 的实测结果是 `BLOCKED=0 WARNINGS=0 CLONE_PRECHECK_OK`。

**它只覆盖上面 11 条克隆机判据里的一条（`dhcp.lan.ignore`），拿到 `CLONE_PRECHECK_OK` 不等于 11 条全绿。** 其余 10 条必须另行逐条只读回读。

它的检查项分三级，只有前两级会改变结论：

```text
能 BLOCK（计入 BLOCKED，rc=1）  BOARD_MATCH / EMMC_SIZE_MATCH /
                                MAC_COLLISION_WITH_SOURCE / LAN_IP_COLLISION_WITH_SOURCE
能 WARN （计入 WARNINGS，rc=0） RELEASE_MATCH / KERNEL_MATCH / RADIO_PATH_MATCH /
                                HOSTNAME_COLLISION_WITH_SOURCE / DHCP_SERVER_ACTIVE
仅打印（永不影响结论）          MANAGED_FILES_PRESENT / CELLULAR_PRESENT /
                                PKG_* / SSH 主机密钥指纹 / PACKAGE_COUNT / OVERLAY_FREE_KB
```

**第三级是坑：`BLOCKED=0 WARNINGS=0 CLONE_PRECHECK_OK` 与「OpenClash 根本没装」「一个 dropbear 主机密钥都没有」「16 个受管件早已存在于一台号称全新的机器上」全部兼容。** 拿退出码当闸门的自动化会就此越过「部署器在主机密钥未固定或不匹配时必须停止」这条约束。主机密钥必须人眼看指纹并写进 `docs/私密/router_known_hosts`，脚本不替你把关。

另外，主机名撞车与 DHCP 双发放在脚本里只是 WARN、rc 仍为 0，而它们的实际后果是「两台同名 DHCP/mDNS 分不清」和「客户端随机拿到两套网关」。**要的是 `WARNINGS=0`，不是 rc=0。**

## 连接设备时的失败处置

下表「现象与真实输出」列均为 2026-09-03 实际观测所得，不是构造示例。

**第一列不全是可 grep 的 token。** 只有 `SSH_LOGIN_FAILED` 是本项目脚本真正打印的常量；`BadAuthenticationType` 是 Python 异常类名；其余是第三方工具输出的英文片段或对现象的描述。要做自动分派就按第二列的真实输出串匹配，不要匹配第一列。

| error_kind | 现象与真实输出 | handling |
|---|---|---|
| `SSH_LOGIN_FAILED` | `openclash-ui-patch/router_readonly.py` 打印 `SSH_LOGIN_FAILED` 并以 rc=1 退出 | 该脚本只试密码认证。出厂 root 无密码时 dropbear 只接受 SSH `none` 认证，须改用 `transport.auth_none("root")`。设备已设密码时，把密码按反引号写进 `docs/私密/商家交付信息.md`，脚本会自动取用 |
| `BadAuthenticationType` | `paramiko.ssh_exception.BadAuthenticationType: Bad authentication type; allowed types: ['publickey', 'password']` | 该设备已设 root 密码，`none` 认证通道已关闭。改走密码认证，凭据同样取自 `docs/私密/商家交付信息.md` |
| `certificate is not yet valid` | `opkg update` 报 `wget returned 5`；单独 `wget` 该 URL 报 `SSL verify error: certificate is not yet valid` | 设备时钟落后于证书签发日期。R3 Mini 没有电池供电的 RTC，冷启动后时间会退回固件构建日期。先 `date -u -s '<当前UTC时间>'` 对时，再 `opkg update`。并确认 `system.ntp.enabled=1` |
| `Unknown package` | `opkg install nikki` 报 `Unknown package 'nikki'.` 与 `opkg_install_cmd: Cannot install package nikki.` | `nikki` 与 `mihomo-meta` 不在 ImmortalWrt 24.10.6 任何官方源里。**处置：跳过，不要找第三方源。** 源机的 Nikki 停止且禁用，克隆机缺它不影响任何已验收功能；确需补装时先向用户确认来源可信，不要自行找镜像 |
| `cannot open` + `openclash_version.lua` | LuCI 首页整体崩溃：`/usr/lib/lua/luci/ucodebridge.lua:23: cannot open /usr/share/openclash/openclash_version.lua: No such file or directory` | OpenClash 包版本与 LuCI controller 版本不匹配。**处置：先只读回读源机 `opkg list-installed \| grep openclash` 拿到版本号**（不要用本表或本文任何地方写的版本号），再从 `https://github.com/vernesong/OpenClash/releases/download/v<版本>/luci-app-openclash_<版本>_all.ipk` 取同版本包，**放 `/root` 不要放 `/tmp`**，`opkg install --force-reinstall <ipk>`。验收：新机 `/usr/share/openclash/openclash_version.lua` 的 sha256 与源机同一文件逐位相同 |
| `HTTP error 404 while loading class file` | 风扇页报 `HTTP error 404 while loading class file "/luci-static/resources/view/system/r3mini-fan-3848230b8f.js"` | 菜单 json 的 view path 带缓存指纹后缀，需要同名 JS 副本存在。**在设备上立刻修**：`cp -a /www/luci-static/resources/view/system/r3mini-fan.js /www/luci-static/resources/view/system/r3mini-fan-3848230b8f.js && rm -f /tmp/luci-indexcache*`，然后刷新页面。副本名以该设备菜单 json 里 `action.path` 的实际值为准。仓库已把该副本纳入 `fan-dashboard/router/`，由 `scripts/router/test-backup-covers-managed-files.sh` 强制两份内容一致，重新部署不会再缺 |
| `status` 返回 `inactive`（无程序打印专用 token） | 恢复配置后 `/etc/init.d/r3mini-fan status` 返回 `inactive`，`ls /etc/rc.d/ \| grep r3mini` 为空 | 配置备份不含 `/etc/rc.d/` 启动符号链接。恢复后必须 `/etc/init.d/<服务> enable` 再 `start`。风扇服务漏做这一步等于**温控不工作**。判据是 `ls /etc/rc.d/ \| grep r3mini-fan` 出现 `S99r3mini-fan` |
